# Read-only maintenance inbox

This contract governs bounded issue intake, durable local attempts, freshness, and maintainer presentation.

## Interface

The inbox wraps the existing bug-readiness agent in a bounded intake workflow.
Ordinary code fetches GitHub issues, tracks observations, decides which snapshots
need work, and renders a local page. Terra still assesses one title/body snapshot;
its tools, prompt v4, and contract v2 are unchanged. This static intake workflow has no GitHub writes, messages, scheduler or
coordinating agents. The separate [operator console](operator-console.md) now
provides a loopback surface for repository briefs and explicit bounded controls.

### Refresh and open

With Node 24, `gh` authenticated, and Copilot credentials configured:

```sh
export ONIONSOUP_AUTH_PATH="$HOME/.local/share/opencode/auth.json"
npm run inbox -- refresh get-bb/bb
```

Open `runs/inbox/get-bb--bb/index.html` in a browser. The default view shows
assessed open reports. Filters show reports ready for investigation, proposed
questions, feature requests, support questions, unclear/other requests, waiting
reports, failures, and observed closures. Search matches issue numbers and titles.
There are no grading forms. Request classification is descriptive, not an
acceptance/rejection decision. Proposed questions are drafts; nothing is sent.

Each card includes the observed source and, when applicable, exact evidence,
assessment identity, and SDK usage. The original run record is linked locally.
The page is a static snapshot: refresh the inbox with the command, then reload it.
To rebuild the page without GitHub or model access:

```sh
npm run inbox -- report get-bb/bb
```

`--directory PATH` selects a different inbox directory on every command.
`--provider copilot|codex` selects the subscription for refresh/retry; Copilot is
the default and the exercised adapter. Model selection is fixed to Terra. A new
inbox pins repository, provider, prompt, and relevant runtime hashes. A later
runtime/provider change requires a new directory, preventing silent reuse of
results generated by a different configuration. Old inboxes remain reportable.

### Bounded intake and freshness

A refresh defaults to one page of 100 GitHub API entries, sorted by latest update,
including open and closed issues. Pull requests are discarded. Observed closures
move out of the active view. Older entries outside the scan window retain their
last observation; absence is never treated as closure. This is a bounded inbox,
not a complete synchronization of the repository.

Before each model assessment, a point read checks the queued issue again for
edits or closure. Stale responses do not replace newer known observations.
Reports changed after that read can still be stale: every result is explicitly
bound to its saved snapshot, not a guarantee of current GitHub state. Invalid or
oversized title/body inputs are visible under Needs attention and never sent to
the model. Display titles may be shortened to 500 characters for those rejected
inputs; model inputs are never silently truncated.

```sh
npm run inbox -- refresh get-bb/bb --max-issues 5 --pages 1 --max-seconds 300
```

`--max-issues` bounds both fresh point reads and new assessments (0–20; default 5).
The initial scan uses at most `--pages` requests (1–3). Thus the default permits
at most six GitHub requests and five assessments. A point read that finds an edit,
closure, or already-assessed content still consumes a point-read slot. `--max-issues 0` updates observations without requesting model work. Each assessment retains
its three-step, 60-second bound; the refresh adds a 1–900-second abort deadline
(default 300). Transport retries may exceed logical model steps. Cancellation is
cooperative and depends on provider abort support, not a process-level watchdog.

The queue considers the last observation time, then recent GitHub updates.
Previously observed reports that fell outside the newest scan are checked first. Repeated refreshes process remaining unassessed reports within the
same bounds. A failed source scan stops processing rather than assessing a stale
queue. Existing valid observations and results remain inspectable.

### Reuse, failures, and interruptions

The content key includes repository, issue number, title, and body. Changes only
to GitHub `updated_at`, comments, or labels do not trigger a new model call. The
original run preserves its full input hash and revision timestamp, while the card
shows the newer observation separately. Changed title/body content gets a new
attempt, retaining the older record. Reverting to previously assessed content
reuses that result under the same pinned runtime. Comments and linked attachments
never enter model context.

Every attempt is saved before model invocation and after termination, using
atomic file replacement. There is no durable per-step resume or power-loss
transaction guarantee. A process crash can leave a `running` attempt whose usage
and outcome are unknown. Refresh skips it, as it skips failed attempts. Failures
remain visible and do not silently spend more quota.

An exclusive `.refresh.lock` prevents concurrent refreshes. Graceful cancellation
releases it; a killed process may leave it behind. Explicit recovery checks that a
lock belongs to this host and its PID no longer exists, then marks unfinished
attempts failed without making model calls:

```sh
npm run inbox -- recover get-bb/bb
npm run inbox -- retry get-bb/bb ISSUE_NUMBER
```

Recovery refuses a live or unverifiable owner. PID reuse can conservatively block
recovery; inspect the lock manually in that case. A crash during recovery can also
leave `.recovery.lock`, which requires inspection before manual removal. Never
remove the lock of a live process.

Retry point-reads one issue and appends at most one new attempt, retaining the
failed attempt. A completed result is not retried. A still-running attempt must
be recovered first. A closed or invalid report is not assessed. A changed report
can instead be picked up by normal refresh. These safeguards reduce duplicate
work; they do not promise exactly-once provider execution after a crash.

### Visibility and limits

`summary.json` contains counts, the latest refresh outcome, attempts, failures,
recorded steps, and SDK-reported token totals. Actual billed cost and quota use
remain unknown. Incomplete calls can have unreported usage. `index.json` stores
observations; `records/` retains attempts; `refreshes/` retains invocation status,
bounds, source-window size, and activity counts. `config.json` records the pinned
runtime. Artifacts stay under ignored `runs/` and include issue text/model output.

A completed refresh can include failed assessments; the CLI exits nonzero for
those or an interrupted/failed refresh. Already-known failures remain visible
without making a later otherwise-successful no-op refresh fail. Application
errors use public codes (`source_error`, `execution_error`, or
`time_limit_or_cancelled`) rather than copying raw transport diagnostics into the
inbox. Source/API errors can be investigated with the authenticated `gh` CLI.

The inbox is an operational pilot. Automated tests establish bounds, reuse,
recovery, and rendering safety. They do not establish that every classification
or question is useful to a maintainer. No human acceptance gate has been waived.

## Rules

Intake MUST remain bounded and read-only on GitHub. Reuse follows the documented freshness checks. Explicit retries preserve prior attempts rather than overwriting their judgments.
